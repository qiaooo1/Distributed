# 演唱会票务与周边履约

以演出运营商作为租户。观众抢到门票后获得限时支付资格，可在后续阶段加购限定周边。付款确认后，取货点收到备货需求，缺货时由平台向符合到货期限的仓库派单。

| 阶段 | 交付边界 | 验收重点 |
| --- | --- | --- |
| 1. 抢票与锁票 | 场次与票档、开售窗口、库存竞争、5 分钟锁票与释放、购票页面 | 并发分配不超库存，同一观众同场最多一张有效票，同一幂等请求返回原单 |
| 2. 模拟支付 | 为锁票单生成独立的模拟付款流水，接收支付确认，支持加购、取货点选择和订单详情 | 重放付款回执不重复结算，付款与释放争用同一订单状态，过期回执可查询 |
| 3. 周边补货派单 | 按取货点和 SKU 汇总付费需求，对缺口生成补货单，根据库存、时效和派单时限选择仓库 | 明确拒单或确认取消后可以转派，超时先查接单回执，相同补货单可幂等恢复 |

## 第一阶段

票务以独立包接入 Scheduler，复用现有租户账号、网关和数据库部署。购票数据放在独立的票务表中，既有报表任务仍由原有调度链路处理。

- Redis 给抢票入口使用独立的固定窗口请求额度。Redis 不可用时，抢票入口返回 503。可售库存以 MySQL 为准。
- 订单创建和扣减票档库存发生在同一数据库事务中。票档行锁把同一票档的竞争串行化，扣减语句同时检查可用数。
- 幂等键在租户和用户范围内唯一。相同键的不同请求返回 409。订单上的可空唯一索引限制同一观众在一场演出中只能有一张有效锁票或已付票。
- 库存扣减时同步写入以数据库时钟计算的 5 分钟截止时间。扫描器按到期索引发现候选，先获取对应票档锁，再做条件状态更新和库存回补。多实例执行时，只有完成状态更新的事务能够回补。
- 购票页面展示可售票档和「我的票」。倒计时按 API 返回的服务器时间校准，超时释放由服务器落实。购票角色只能进入票务页面。

默认演示账号为 `acme / buyer`，密码与其他演示账号相同。演示环境初始化一个在售场次和一个尚未开售的场次。每次重启复用初始化过的库存。

| 接口 | 用途 |
| --- | --- |
| `GET /api/tickets/events` | 返回本租户的场次、票档、开售状态和服务器时间 |
| `POST /api/tickets/events/{eventId}/reservations` | 传入 `{"offerId":"票档 UUID"}` 和 `Idempotency-Key`，尝试锁一张票 |
| `GET /api/tickets/reservations` | 查看本人最近的 50 笔锁票 |
| `GET /api/tickets/reservations/{id}` | 查询本人一笔锁票的最新状态 |

管理员、运营和购票角色可抢票。只读角色可查看票务页面。第一阶段的有效业务状态为锁票中和已过期。模拟支付阶段会在同一票档锁顺序下添加已支付状态。

## 后续事务设计

**模拟支付。** 付款确认先锁同一票档，再尝试将付款截止前的锁票置为已支付。超时释放使用相同的锁顺序。模拟流水的交易号及付款请求键独立唯一。已支付事件通过新的票务 Outbox 投递，供备货流程消费。

**备货与补货。** 按租户、场次、取货点、取货时段和 SKU 汇总已支付需求。库存不足时创建带截止时间的补货单。每次派单保留仓库、分配数量、预计到达和回执状态。派单 Worker 中断后，先用原派单幂等号查询仓库，再根据确认结果继续处理。可沿用 JobLab 的租约思路，另外定义派单命令和结果协议。
